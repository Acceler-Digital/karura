# D8: システムテスト計画書

## 遵守すべき重要ルール

1. **上位文書の内容を転記しない**: 全体テスト計画書・テストポリシーにある内容は書き写さず、該当の見出しへのリンクを記載し、システムテスト固有の差分だけを記載する。差分が無ければ「全体テスト計画に準拠」と記載する。リンクは見出しのアンカーまで含める。
2. **template の見出しを無断で削除・統合しない**: 該当が無い見出しも残す。番号は全体テスト計画書と揃えているため欠番があるが、詰めない。
3. **ST（システムテスト）で実行できないものは対象外にする**: テストスコープの対象外とし、どのテストレベルで扱うかを対象外の理由に記載する。
4. **ID を振り直さない**: 採番済みの `STPLAN-SCOPE-*` は変えず、欠番も再利用しない。

## 処理

### 1. 分岐する

- もし `docs/D8.test-plan/system-test-plan.md` が無いなら、§2（新規作成）に進む。
- それ以外なら、§3（更新）に進む。

### 2. 新規作成

#### 2.1 はじめにとテストの背景を記載する（1〜2章）

- **はじめに**: この計画書で何を決め、誰が何に使うのかを1〜2文で記載する。
- **テストアイテム**: C4モデル レベル1の対象システムごとに1行とする。概要は、「誰が何をし、どこまで進めるシステム。」の1文のあと、`<br>` で「対象は次を結合した状態。」と、役割ごとの `・` で全コンテナの名称とIDを記載する。
- **テストスコープ**: `FUNC-*`・`BATCH-*` ごとに対象／対象外を判断する。対象には `STPLAN-SCOPE-*` を振る。システムごとの違いは、テストアイテム列で区別して記載する。対象／対象外は、機能一覧・バッチ一覧のほか、紐づくユースケースとユーザーストーリーを見て判断する。バッチ一覧が無いときは `BATCH-*` は無いものとして扱う。
- **対象外の理由**: ST で実行できないものは、なぜ実行できないかと、どのテストレベルで扱うかを記載する。C4モデル レベル2シーケンスで外部システムとやり取りするものでも、スタブで代替できるなら対象とする。
- **優先度**: 初期値は、テスト戦略書1章の品質リスクマップのプロダクトリスク（高・中・低）とする。戦略書が無いときは中で仮置きし `【要確認】` を付ける。プロダクト要求仕様書の正常系、ユーザーストーリー、ユースケースを見て、終点まで届く機能は一段階上げ、イレギュラー対応にしか無い機能は一段階下げる。高より上、低より下にはしない。
- **優先度の根拠**: 各行を「〜のため」で記載する。初期値の行は `テスト戦略書 リスクレベル(高・中・低)のため`、戦略書が無い行は `テスト戦略書のリスクレベルが無いため【要確認】` とする。終点まで届く機能は届くために要ることを、イレギュラー対応にしか無い機能は終点までの流れに要らないことを、「〜のため」で記載する。表の下には、初期値と、終点まで届く機能は一段階上げ、イレギュラー対応にしか無い機能は一段階下げることを記載する。
- **前提条件及び制約**: システムテスト固有の前提・制約だけを記載する。

#### 2.2 テスト戦略を記載する（5章）

- **5.1 テストタイプ**: 全体テスト計画書のテストタイプが、システムテストのスコープに当てはまるかを確かめる。
- **5.3 テスト設計技法**: 全体テスト計画書の技法を前提に、スコープへ当てはまる技法をすべて記載する。同じ処理の値域・区分値は同値分割、その端は境界値、業務状態を進める操作は状態遷移、流れの分かれはユースケース試験。選定理由は分かれ方を「〜ため。」で記載し、区分の中身と画面の文言は記載しない。複数のときは「〜ため、技法名。」とする。画面設計書が無いときは、シーケンスと機能一覧から仮置きし `【要確認】` を付ける。
- **5.4 開始及び終了基準**: テスト設計・実装とテスト実行のそれぞれについて記載する。テスト実行の開始基準には、計画書の承認、テスト観点・仕様書の承認、テストデータ・環境（対象のデプロイを含む）の準備完了を含める。終了基準には、対象スコープのうち最も高い優先度のテストケースがすべて実行・合格していること、修正した不具合の修正確認テストがすべて合格していること、リグレッションテストが完了していることを記載する。重大度の低い不具合は、修正要否の判断が済んでいれば残っていてもよい。
- **5.6〜5.11**: 全体テスト計画書の記述がシステムテストに当てはまるかを確かめ、外れる点があれば差分を記載する。
- **5.12 中断及び再開基準**: 差分を記載する場合、テスト戦略書で定義されているテストを削る条件と整合性が保たれていることを確認する。テスト戦略書が無いときは、仮置きし `【要確認】` を付ける。
- **5.13 テストポリシーからの逸脱**: テストポリシーから外れる点があれば記載する。

#### 2.3 活動とスケジュールを記載する（6〜7章）

全体テスト計画書の記述がシステムテストに当てはまるかを確かめ、外れる点があれば差分を記載する。全体テスト計画書が無いときも「全体テスト計画に準拠」とリンクを記載し、中身は仮置きしない。

#### 2.4 仕上げる

「完成時のセルフチェック」を実施する。

### 3. 更新

- インプットした成果物で変わった箇所に関わる見出しだけを §2 の手順で見直す。新しい行には、最大値の次の ID を振る。
- もしテストスコープを変えたなら、`docs/D9.test-design/test-perspectives.md` の見直しが必要になる旨をユーザーに伝える。

## 完成時のセルフチェック

- template の全見出しがある
- テストアイテムがレベル1の対象システムごとに1行で、概要に全コンテナのIDが役割ごとの・で現れている
- 機能一覧の全 `FUNC-*` と、バッチ一覧があるときの全 `BATCH-*` が、テストスコープのいずれかの行（対象／対象外）に現れている
- 対象外の行すべてに、実行できない理由と、どのテストレベルで扱うかが記載されている
- テストスコープの対象の行すべてに優先度とその根拠が入り、優先度の決め方が記載されている
- 対象の行の優先度が、プロダクトリスクを初期値とし、プロダクト要求仕様書の正常系とユーザーストーリーとユースケースを見て、終点まで届く機能は一段階上げ、イレギュラー対応にしか無い機能は一段階下げた結果と一致している。戦略書が無い行の根拠に `【要確認】` がある
- 5.3 で参照している `STPLAN-SCOPE-*` がすべてテストスコープに存在し、テストスコープの対象の `STPLAN-SCOPE-*` がすべて 5.3 のいずれかの技法に対応付けられている
- 5.3 の技法が、同値分割は値域・区分値、境界値はその端、状態遷移は状態を進める操作、ユースケース試験は流れの分かれに対応している。選定理由が「〜ため。」で終わっている。区分の中身や画面に出す文言が記載されていない
- 5.4 の開始基準・終了基準が、テスト設計・実装とテスト実行の両方について記載されている
- 全体テスト計画書を参照する見出しすべてに、参照先のアンカーまで含むリンクが記載されている
- 差分が無い見出しに「全体テスト計画に準拠」と記載されている
- `STPLAN-SCOPE-*` に重複が無く、更新時は既存の ID と内容の対応が変わっていない
