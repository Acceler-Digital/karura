# KARURAハンドブック

本ハンドブックは、KARURA を使って実際に開発を進める人のための手引きです。リポジトリ本体の README が「何が入っていて、どう動かすか」を案内するのに対し、本書はそれだけでは伝わらない **KARURA の考え方(なぜこのフェーズ構成なのか)** と、**各成果物を作り・レビューするときの実務上の勘所** を扱います。

## KARURA が目指すもの

KARURA がプロジェクトで実現しようとするのは、突き詰めれば次の2点です。

- **仕様通りの正確なコードを書くこと**
- **品質担保**

成果物フロー(D0–D11 のフェーズ分割)も、各フェーズのスキルやテンプレートも、すべてはこの2点に奉仕する手段です。本書を読むときは、どの作法も最終的に「正確なコード」と「品質担保」のどちらか(あるいは両方)にどう効くのか、という視点で捉えてください。

## なぜ成果物フロー(フェーズ分割)なのか

大規模・ミッションクリティカルな開発で最大の敵は **曖昧さ** です。業務要求から実装まで一気に書こうとすると、解釈の幅が残ったままコードになり、仕様とのズレ・手戻り・品質劣化を生みます。

KARURA は工程を多数の成果物に分割し、各成果物が **上流を入力として少しずつ曖昧さを削る** 構造をとります。実装に着く頃には、仕様が一意に定まり、かつ「どの要求から来た仕様か」を辿れる状態になっています。これが正確なコードと品質担保の土台です。さらに、上流が変わっても、フローを辿れば下流のどこに影響するかが分かります(変更伝搬)。

成果物フローの全体像と依存関係の実物は、[成果物フロー](../docs/D0.project-management/artifact-flow.md) を参照してください。

## フェーズ全体像(D0–D11)

各フェーズは「何を確定させ、次のフェーズに何を渡すか」という役割を持ちます。上流ほど業務に近く、下流ほど実装に近づきます。

| フェーズ | このフェーズで確定させること | 本リポジトリでの収録 |
|---|---|---|
| D0 プロジェクトマネジメント | 全フェーズ横断の進行・課題・リスク管理 | 一部(成果物フロー等のメタ情報) |
| D1 ビジネス要求 | 事業の狙いと業務要求を業務言語で確定 | 収録済み(9 スキル) |
| D2 システム要件 | 業務要求をシステムの機能能力へ翻訳 | 収録済み(3 スキル) |
| D3 システム設計 | 機能能力を実装可能な設計へ具体化 | 拡張予定 |
| D4 実装・UT・内部結合テスト | 設計をコード化し検証 | 拡張予定 |
| D5 E2E テスト(ITb) | 結合された機能を利用シナリオで検証 | 拡張予定 |
| D6 システムテスト | システム全体を要件に照らして検証 | 拡張予定 |
| D7 リリース | 本番への展開 | 拡張予定 |
| D8 テスト計画 | テスト全体の方針・範囲を定義 | 拡張予定 |
| D9 テスト設計 | テストケースを設計 | 拡張予定 |
| D10 システム運用要件 | 運用に求められる要件を定義 | 拡張予定 |
| D11 システム運用設計 | 運用の具体設計 | 拡張予定 |

本書のフェーズ別ガイド(後半)は、現時点でスキルを収録している D1・D2 を対象にしています。

## すべての成果物に共通する原則

ここで挙げる原則は、品質担保を成果物レベルで効かせるための仕掛けです。どのフェーズの作業・レビューでも共通の着眼点になるため、フェーズ別ガイドに入る前に押さえてください。

### 上流から直接生成する(作業はレビュー中心)

KARURA のスキルは、原則としてヒアリングを挟まず **上流成果物から直接生成** します(例外は、上流を持たない最上流のビジネス要件定義書だけ)。したがって作業の主戦場は「ゼロから書く」ことではなく、**生成物をレビューして直す** ことです。スキルが推測・仮置きで埋めた箇所には要確認マーカーが付くので、レビューはまずそこを起点に進めます。

### フェーズの抽象度に留まる(下流の How を先取りしない)

各成果物は自身のフェーズの抽象度に留まり、下流フェーズで決めるべき事項(How)を先取りしません。実装を想起させる語が出てきたら、それは下流に降ろすべき兆候です。レビューでの典型的な指摘箇所になります。

| フェーズ | 留まる抽象度 | 先取りしない(下流の How) |
|---|---|---|
| D1 ビジネス要求 | 業務言語 | 機能名・画面・API・データ等のシステム用語 |
| D2 システム要件 | システムが提供する機能能力(capability) | 画面名・API名・テーブル/カラム名・実装技術 |
| D3 システム設計以降 | 設計・実装の How | — |

### トレーサビリティ(全件網羅)

上流が定義した ID(`ACT-*` / `DOM-*` / `US-*` / `UC-*` 等)は、下流成果物の「関連 ID」列で取りこぼさず参照します。上流の全 ID が下流のいずれかの行に少なくとも1回現れる状態を保つことで、仕様の根拠が追跡でき、変更時の影響範囲も辿れます。トレーサビリティは品質担保の幹であり、レビューでは「上流の全項目が下流に対応しているか」を必ず確認します。

### 粒度の統一(ユースケース単位)

シーケンス図は **1 ユースケース = 1 シーケンス図** の単位で作成し、実装工程でもこの **ユースケース単位** を作業の基準とすることを想定しています。要求 → 設計(シーケンス図)→ 実装 を同じ単位で貫くことで、仕様とコードの対応が崩れません。そのため、ユースケースは「1本のシーケンス図に無理なく収まるオペレーション粒度」に割っておくことが重要で、これが下流すべての作業単位を左右します。

## フェーズ別ガイド

ここからは各成果物を、冒頭に基本情報(ファイル名・コマンド・目的)、続けて作り込み・レビューの勘所を解説する形で扱います。コマンドは KARURA プラグインを導入したプロジェクトで Claude Code を起動して実行するスラッシュコマンド(`/karura:` 名前空間)です。ファイル名は成果物本体の Markdown で、あなたのプロジェクトの `docs/<フェーズ>/` 配下に配置する想定です。

### D1 ビジネス要求

事業の狙いと業務要求を **業務言語で** 確定させるフェーズです。ここで決めたことが下流すべての根拠になるため、システム実装の語を持ち込まず、業務として正しいかにレビューの重心を置きます。生成順は、ビジネス要件定義書を起点に、アクター・ドメインの土台を固め、プロダクト要求 → 各種要求仕様 → 利用者視点(ユーザーストーリー・ユースケース)へと具体化していきます。

#### ビジネス要件定義書

| ファイル名 | コマンド | 目的 |
|---|---|---|
| `business-requirement-document.md` | `/karura:d1-business-requirement-document` | 事業観点の要求を定め、全成果物の根拠とする |

フロー全体の出発点であり、唯一上流を持たないためヒアリングから起こします。ここで定めた事業目的・KPI・スコープ・リスクが、以降すべての成果物の判断基準になります。逆に言えば、ここが曖昧なまま下流へ進むと、各成果物が別々の前提で作られ、最後に整合しなくなります。

作成時の勘所は、抽象的な「狙い」を、測定可能な KPI と、内外を線引きしたスコープに落とし込むことです。レビューでは、KPI が数値と期日で検証可能か、スコープの除外事項まで明示されているか、そして個々の要求が事業目的に紐づいているか(目的なき要求が紛れていないか)を確認します。

#### アクター一覧

| ファイル名 | コマンド | 目的 |
|---|---|---|
| `actor-list.md` | `/karura:d1-actor-list` | 全人間アクターを洗い出し、下流が共通参照する登場人物表を作る |

システムに関わる人間アクターを洗い出し、以降の成果物が共通で参照する「登場人物の正本」を作ります(TOGAF の Actor Catalog 相当)。PRD・ユーザーストーリー・C4・シーケンス図など下流の広範囲がこの ID(`ACT-*`)を引くため、ここでの抜けや粒度のブレは下流全体に波及します。

勘所は、人事上の肩書(課長・主任 等)ではなく、システムから見た役割でアクターを割ること。同じ人物が複数の役割を担う場合は、役割ごとに分けます。レビューでは、業務に登場する人物や外部の関与者まで網羅できているか、役割の粒度が揃っているか、下流から参照しやすい命名になっているかを見ます。

#### ドメイン定義書

| ファイル名 | コマンド | 目的 |
|---|---|---|
| `domain-definition-document.md` | `/karura:d1-domain-definition-document` | プロダクトが扱う業務領域(問題空間)を網羅・分類する |

プロダクトが扱う業務領域を網羅・分類した、問題空間の地図です。重要なのは、これは「業務として何を扱うか」の整理であって、DDD の Bounded Context のような実装・解空間の境界とは別レイヤーだという点です。ここで切ったドメイン(`DOM-<ニーモニック>`)が、後続のドメイン要求仕様書の「1 ドメイン = 1 冊」の単位になるため、切り方が下流の文書構成をそのまま決めます。

勘所は、業務領域を漏れなく・重複なく(MECE に)分けること。レビューでは、実装都合(システム構成やチーム編成)を問題空間に持ち込んでいないか、粒度が極端に粗い/細かいドメインがないかを見ます。

#### プロダクト要求仕様書(PRD)

| ファイル名 | コマンド | 目的 |
|---|---|---|
| `product-requirement-document.md` | `/karura:d1-product-requirement-document` | 方針・概念・体験・制約・受け入れ基準を定める(要求 ID は持たない) |

プロダクトの「方針・概念・体験・制約・受け入れ基準」を定める文書で、KARURA では具体的な横断要求(機能・非機能 等)を持たせず、要求 ID も振りません。具体要求は下流のドメイン共通要求仕様書・ドメイン要求仕様書に降ろします。これは「PRD は何を作るかの方向を決め、要求仕様が具体を引き受ける」という役割分担です。

勘所は、書いている最中に機能要求・非機能要求を列挙し始めたら、それは降ろすべき兆候だと気づくこと。レビューでは、受け入れ基準が後工程で検証可能な形になっているか、個別要求を PRD が抱え込んでいないか(役割の越境)を見ます。

#### ドメイン共通要求仕様書

| ファイル名 | コマンド | 目的 |
|---|---|---|
| `domain-common-requirement-document.md` | `/karura:d1-domain-common-requirement-document` | 3 ドメイン以上で横断的に効く具体要求を集約する |

3 ドメイン以上に横断的に効く具体要求(機能・非機能・UI/UX・セキュリティ・データアクセス・法務)を一手に集約する文書です。ドメイン要求仕様書群(個別)とは並列・MECE の関係にあり、横断要求は本書が単独で責務を持ち、個別ドメインで言い換えません。

勘所は、「この要求は本当に複数ドメインに効くのか、それとも特定ドメイン固有か」を毎回判定し、置き場所を 1 つに決めること。両方に書くと MECE が崩れ、変更時に二重メンテナンスになります。レビューでは、個別ドメイン側に同じ要求が重複していないか、逆に特定ドメインだけの要求が共通側に紛れ込んでいないかを見ます。

#### ドメイン要求仕様書

| ファイル名 | コマンド | 目的 |
|---|---|---|
| `domain-requirement-document.md` | `/karura:d1-domain-requirement-document` | ドメインごとに固有の業務ルール・業務状態遷移・業務運用を具体化する |

ドメインごとに 1 冊作成し、そのドメイン固有の業務ルール・業務状態遷移・業務運用(イレギュラー対応)を具体化します。ここで記述する業務状態遷移の「1 遷移」が、下流のユースケース(= 1 シーケンス図)の素になるため、状態遷移を丁寧に洗うことが下流の質を左右します。

勘所は、共通要求と重なる内容を書かないこと、そして業務言語に留まりシステム実装の語を持ち込まないこと。レビューでは、業務状態の遷移を網羅できているか(抜け・行き止まりがないか)、共通要求との重複がないか、イレギュラー(中断・例外)を業務目線で拾えているかを見ます。

#### ユーザーストーリー一覧

| ファイル名 | コマンド | 目的 |
|---|---|---|
| `user-story-list.md` | `/karura:d1-user-story-list` | 利用者視点の要求を Connextra 形式のフラット表で一覧化する |

利用者視点の要求を Connextra 形式(「〜として、〜したい、なぜなら〜」)で、1 ストーリー 1 アクターのフラットな表に一覧化します。ドメイン別の章分割をせず、スプレッドシートへ移送しやすいフラット構造にするのが特徴です。

勘所は、1 ストーリーに複数アクター・複数価値を詰め込まないこと、そして実現手段(How)ではなく利用者が達成したい価値(What / Why)で書くこと。レビューでは、各ストーリーが検証可能な価値になっているか、上流(PRD・ドメイン要求)の要求を取りこぼしていないか、粒度が揃っているかを見ます。

#### ユースケース一覧

| ファイル名 | コマンド | 目的 |
|---|---|---|
| `use-case-list.md` | `/karura:d1-use-case-list` | 業務オペレーションを「1 UC = 1 シーケンス図」の単位に割る |

業務オペレーションを「1 UC = 1 シーケンス図」の単位に割った一覧で、これが下流の設計・実装の作業基準単位になります。KARURA で最も粒度設計が効く成果物のひとつです。

勘所は、工程まるごとを 1 UC にしないこと。たとえば「設計書作成」を 1 UC にせず、「商品・特約選択」「保険料試算」「意向整合検証」「プラン比較提示・確定」のように、1 本のシーケンス図に無理なく収まるオペレーションへ割ります。同一アクターのインライン例外(IRR)は同一 UC の alt 分岐に、別アクター・別トリガの収束業務やプロダクト共通能力(認証/中断再開/通知 等)は独立 UC に切り出します。レビューでは、各 UC が 1 本のシーケンス図に収まる粒度か、上流の全項目が UC に取りこぼしなく対応しているか、画面名・API 等の D2 語が混入していないかを見ます。

#### 画面コンセプト集

| ファイル名 | コマンド | 目的 |
|---|---|---|
| `screen-concepts.md` | `/karura:d1-screen-concepts` | 画面体験コンセプト(方向性・原則・代表シーン)を合意できるサイズに整理する |

プロダクト全体の画面体験コンセプト(体験方向性・体験原則・代表シーン 2–3)を、ビジネスサイドが議論・合意できるサイズに整理します。全画面の網羅は D2 の画面要件群に降ろし、本書はコンセプトと代表シーンに集約するのが役割分担です。KARURA では画面に関わる成果物は Figma を併走させ、Markdown 側が「言葉(方向性・原則・代表シーンの記述)」、Figma 側が「絵(ムードボード・代表シーンのラフ)」を持ちます。

勘所は、D1 段階では Figma 投資を代表シーン数枚に絞り、全画面を描こうとしないこと。レビューでは、体験原則が下流のワイヤーフレーム・画面要件の判断基準として使える具体性を持っているか、コンセプトが肥大化して画面要件の領域に踏み込んでいないかを見ます。

### D2 システム要件

D1 で確定した業務要求を、**システムが提供する機能能力(capability)** へ翻訳するフェーズです。ここでの抽象度は「何ができるか」であり、画面名・API 名・テーブル名といった実装の How(D3)はまだ持ち込みません。レビューでは、D1 の要求を取りこぼさず能力に落とせているか、実装語が紛れていないかが共通の着眼点になります。

#### 機能一覧

| ファイル名 | コマンド | 目的 |
|---|---|---|
| `function-list.md` | `/karura:d2-function-list` | D1 成果物を「システムが提供する機能能力」へ翻訳する |

ユースケース一覧をはじめとする D1 成果物を、「システムが提供する機能能力(capability)」へ翻訳した一覧です。D2 の抽象度は「何ができるか」であり、画面名・API 名・テーブル名といった実装の How(D3)はまだ持ち込みません。

勘所は、ユースケースの操作を機能能力に過不足なく対応させること、そして翻訳の際に実装語へ滑り落ちないこと。レビューでは、ユースケースの全件が機能に落ちているか(トレーサビリティ)、能力レベルを超えた実装語が混入していないかを見ます。

#### 外部システム一覧

| ファイル名 | コマンド | 目的 |
|---|---|---|
| `external-system-list.md` | `/karura:d2-external-system-list` | 連携する外部システム/サービスを台帳化する |

本システムが連携する外部システム/外部サービスを `EXT-*` で台帳化します。C4 モデル・シーケンス図・連携設計がこの台帳を参照するため、ここが連携の「正本」になります。入力は主に PRD のプロダクト概要で引いた「内製/外部の境界」です。

勘所は、連携先を漏れなく挙げること、そして内製と外部の線引きを PRD と一致させること。レビューでは、連携先の網羅性、内製/外部の境界が上流と矛盾していないか、各外部システムの役割が識別できるかを見ます。

#### C4 モデル レベル1(システムコンテキスト図)

| ファイル名 | コマンド | 目的 |
|---|---|---|
| `c4-level1-system-context.md` | `/karura:d2-c4-level1-system-context` | 対象システムを中心に、利用者と外部システムを図示する |

対象システムを中心に、利用者(アクター)と連携先の外部システムを Mermaid で図示する、最も俯瞰のシステム構成図で、C4 のレベル1(システムコンテキスト)に当たります。KARURA 全体では C4 を L1 とコンテナ(L2)までで運用し、コンポーネント(L3)・コード(L4)は描きません。L3・L4 まで描くと設計・実装の How に踏み込み、コードとの二重管理で図の保守コストが実態に見合わなくなるためです

勘所は、ここで登場人物や外部システムを定義し直さず、アクター一覧(`ACT-*`)・外部システム一覧(`EXT-*`)の ID をそのまま流用すること。レビューでは、ID を独自に振り直していないか、システム境界の内外(何が対象システムで何が外部か)が正しく置かれているかを見ます。
