# D3: アプリケーションアーキテクチャ

## 遵守すべき重要ルール

1. **レベル2を具体化する**: 利用者・コンテナ・外部サービスはレベル2と1対1で対応させ、コンテナの分け方・責務・連携方式を本書で変えない。本書はレベル2を具体化したものなので、名称には実体を括弧で添えてよく、レベル2側の名称を本書に合わせて直させない。配置に要る要素(秘密情報の置き場所・ログの置き場所・実行の起動元 等)は本書で足してよい。レベル2側に過不足があるなら、本書で辻褄を合わせず、レベル2の見直し要否をユーザーに確認する。
2. **決めきる**: 実行基盤・データストア・外部サービスの実体・コンテナの作り方は本書で決める。上流が「AIサービス」「記録手段」のように実体を伏せていても、本書では製品名・サービス名まで決め、「未確定」「〜等」のまま残さない。ADRに決定があればそれに従い、ADRに基づかない選定には要確認マーカーを付す。
3. **コンテナの中身まで書く**: 各コンテナを何で作るかを書く。実行の入口・内部の分け方・主なライブラリを示し、外部サービスに依存する処理をどこに閉じ込めるかを明らかにする。連携方式が非同期のコンテナ間は、その引き渡しを何で実現するかまで書く。
4. **環境で揃えるものと変えるものを分ける**: 環境ごとに変えるのは、配置先・規模・実行の起こし方・接続先・秘密情報とログの置き場所に限る。コンテナの分け方・中身・処理の流れ・データストア製品は全環境で揃える。

## 処理

### 1. 分岐する

- `docs/D3.system-design/architecture-design/application-architecture.md`が存在しないなら、§2(新規作成)に進む。
- それ以外なら、§3(更新)に進む。

### 2. 新規作成

引数の指定にかかわらず、全環境の章を作る(環境をまたぐ章と揃わなくなるため)。

#### 2.1 上流を読む

レベル2から、配置するコンテナ・外部サービス・利用者と、線でつながる組み合わせ・向き・連携方式を控える。レベル2シーケンスから、実行を起こす契機・外部サービスの操作のしかた・中断と再開の扱いを控える。PRDから、稼働形態・処理量・運用費の上限・認証情報の扱い・体制の制約を控える。もしADRが存在するなら、承認済みの決定だけを採用する。

#### 2.2 環境を決める

ローカル開発環境・Dev環境・Staging環境・本番環境を候補とし、プロジェクトの規模・体制・費用の制約から要るものを選ぶ。選ばなかった環境も§環境の表に行を残し、扱い(作る / 設計のみ / 作らない)と、そう決めた理由を書く。月額の見込みは環境ごとに書き、推測なら要確認マーカーを付す。件数や量に応じて増える課金があるなら、何件・何GBで見積もったかを要確認に添える。

#### 2.3 技術を決める

- 実装言語・実行基盤・データストア・実行の起こし方・秘密情報とログの置き場所を選ぶ。上流の稼働形態・処理量・運用費の上限・認証情報の扱い・体制の制約を満たす組み合わせのうち、運用の手間が少なく費用の小さいものを選ぶ。
- 上流で実体が伏せられている外部サービスは、ここで製品名・サービス名を決め、レベル2の名称の後ろに括弧で添えて書く。
- 同じ要素を環境ごとに違う製品にしない。規模や料金体系だけを環境で変える。
- 費用だけで選ばない。その用途のために作られたサービスを既定とし、費用を理由に別の選択肢へ寄せるなら、何を諦めたかと代替案を要確認に書く。
- 選定の前に、扱う値の大きさと件数の上限を確かめる。鍵ファイルのようにKB単位の値を置けるか、1件あたりの課金がいくらか、上限に余裕があるかを見る。上限ぎりぎりの選択肢は、安くても採らない。
- §技術選定の選定理由には、根拠としたADR・PRDのIDを書く。

#### 2.4 コンテナの中身を決める

レベル2のコンテナごとに、実行の入口・内部の分け方・主なライブラリを決める。

- 内部の分け方は、外部サービスに依存する処理・上流で定めた判定や推論・データの読み書きを、それぞれ別の受け持ちに分ける。外部サービス側の変更で直す範囲を、その外部サービスを扱う受け持ちに閉じ込める。
- レベル2で非同期としたコンテナ間の引き渡しは、何に積んで、いつ誰が読み取るかまで決める。環境ごとに違う仕組みにしない。
- 上流の非機能要求(処理量・再開時の重複防止 等)を満たすうえで、中身の作りに効く点があれば§補足に書く。

#### 2.5 図を描く

- 環境ごとに1枚、`flowchart LR`で描く(C4専用記法は使わない)。左から順に、利用者・環境・外部サービスを置く。
- 環境の`subgraph`の中に実行基盤の`subgraph`を置き、その中にコンテナのノードを入れる。データストアは円柱(`[( )]`)で実行基盤の外に置く。
- コンテナと外部サービスのノードにはレベル2の名称を書き、実体を決めたなら括弧で添える。本書で足した要素には製品名またはサービス名を書く。
- 線は呼び出す側から呼び出される側へ引き、ラベルにやり取りする内容と連携方式(同期 / 非同期)を書く。コンテナどうし・コンテナと外部サービスの線は、レベル2にある組み合わせと向きに従う。
- ノード名と線のラベルは1行12文字以内で改行する。
- もし外部サービスが環境の右に並ばないなら、非表示の線(`~~~`)で位置を整える。

#### 2.6 表と箇条書きを埋める

- 本書では要素にIDを振らず、名称で対応づける。
- §構成要素の「配置するコンテナ」列には、その要素が受け持つコンテナの名称を書く。コンテナを受け持たない要素は「—」とする。
- §外部サービスへの接続には、接続方法・書き込みの有無・認証情報の渡し方を書く。環境ごとに接続先が分かれるなら、その違いと理由を書く。
- §補足には、図だけでは読み取れない前提(選定の前提・環境をまたぐ制約・本スキルの原則から外した点とその理由 等)を、1項目1〜2文で箇条書きにする。
- §実行とデプロイ・§監視と復旧・§秘密情報と権限には、当該環境で何をどこで行うかを箇条書きにする。手順書そのものは本書には書かない。

### 3. 更新

- 引数で環境が指定されているなら、その環境の章だけを§2の手順で見直す。指定が無いなら全環境の章を見直す。
- §環境・§技術選定・§コンテナの中身・§外部サービスへの接続は環境をまたいで効くため、ここを変えたときは、引数の指定にかかわらず全環境の章を合わせて見直す。
- もしレベル2でコンテナが分割・統合され、配置先の引き継ぎ先が決まらないなら、ユーザーに確認する。

## 完成時のセルフチェック

- レベル2の全コンテナが、§コンテナの中身の行と、作る環境の§構成要素の「配置するコンテナ」列に現れている
- 図のノードが、§構成要素の行と過不足なく対応している
- 図に現れる外部サービスが、レベル2の外部サービスと1対1で対応している(名称に実体を添えるのはよい)
- コンテナどうし・コンテナと外部サービスの線の組み合わせと向きが、レベル2の線と一致している
- レベル2で非同期としたコンテナ間の引き渡しについて、実現する仕組みが書かれている
- 製品名・サービス名が決まっていない要素や、「未確定」「〜等」で濁した記述が残っていない
- §技術選定の全行に選定理由があり、ADRに基づかない行に要確認マーカーが付いている
- `{{`が残っていない
